# B3 staged SQL modules — offline review only

`backend_role_access_candidate.sql` is a **fragment**, not an independently runnable migration. It assumes the objects created by B's 001 exist. In the approved release task, merge its reviewed statements into one canonical Supabase 001 **after** table/approval creation and **before** COMMIT; keep the 001 transaction and lock/statement timeouts. Running B's 001 and then this fragment separately would violate the one-version release plan.

The role is created with LOGIN but no password in SQL. A Project Owner/operator must provision a strong credential through an approved interactive channel and place it in a secret manager, then verify `current_user` on the intended Development session. Do not place a password, URL or project ref in SQL, shell history or Git. On Supabase shared session pooler, a custom role uses the role plus project suffix in the username and port 5432; copy host/user details from the Dashboard Connect panel. Runtime Prisma must use this limited role only after role/RLS tests. Admin migration credentials stay separate.

The fragment grants cross-row SELECT/UPDATE to a trusted backend role because the current six business tables have no tenant column/policies to scope it. It does not grant client roles access to ledger or idempotency. The existing broad `authenticated` policies and direct Flutter/RPC writes remain security blockers outside this candidate. `preflight_assertions_read_only.sql` and `postcheck_assertions_read_only.sql` are proposed read-only gates; `DO` assertion behavior and all role/policy semantics have **not** been executed on PostgreSQL 17.
